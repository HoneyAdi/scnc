## 2A. Posting lock â€” database-level enforcement (normative)

A voucher is created in an editable state and frozen at posting, inside ONE transaction (see Â§3). Enforcement is at the database layer so it holds regardless of API bugs, and it applies equally to Super Admin sessions using the normal application role:

1. **Grants (who can write at all):** on all financial tables (`vouchers`, `voucher_lines`, `fee_dues`, `fee_receipt_lines`, `supplier_invoices`, `payment_allocations`, `concessions`, `refunds`, `audit_log`) the application role (`scnc_app`, `scnc_app_test` in tests) holds `SELECT` plus `EXECUTE` on the Â§2Bâ€“Â§2C functions ONLY â€” NO `INSERT`/`UPDATE`/`DELETE` (no grant, never extended). Every voucher/line/subledger mutation therefore executes inside a migration-owned `SECURITY DEFINER` function running as owner, never as direct application DML; direct writes fail on privilege before any trigger fires. The invoker role (`scnc_reversal_invoker`) holds `SELECT` plus `INSERT` on `vouchers`/`voucher_lines` only (to assemble reversing drafts) â€” explicitly NO `INSERT` on `audit_log`: the reversal/adjustment audit row is written exclusively inside the definer function, in the same transaction as the flag flips, attributed to the server-resolved actor. It additionally holds `EXECUTE` on the reversal/adjustment linkers only â€” NO `UPDATE`/`DELETE` anywhere, NO DDL, NO membership in any other role, and `scnc_app` is never a member of it (`SET ROLE` forbidden).
2. **Triggers (what shape any write may take â€” migration-owned, fire for every role including owner):**
   - `trg_voucher_immutable`: `BEFORE UPDATE OR DELETE ON vouchers FOR EACH ROW` â€” `DELETE` is always rejected. `UPDATE` is allowed ONLY for these single-step pairs with all other columns unchanged (except managed `version`/`lines_hash` written by the transition functions themselves): `draftâ†’pending_approval` (submit), `pending_approvalâ†’edit_requested` (edit request opened), `edit_requestedâ†’pending_approval` (edit applied or edit rejected), `pending_approvalâ†’approved_for_posting` (posting approved), `pending_approvalâ†’rejected` and `approved_for_postingâ†’rejected` (posting rejected), `approved_for_postingâ†’posted` (posting, only with a bound posting approval for the exact version+hash in the same transaction), `draftâ†’posted` (reversing/adjusting leg ONLY, only with a bound reversal/adjustment approval naming it as the reversing voucher in the same transaction), `postedâ†’reversed` (only with a linked reversing voucher in state `posted` in the same transaction), `draft|pending_approval|edit_requested|rejected â†’ cancelled` (cancel with reason), `rejectedâ†’draft` (audited resubmit). Every other transition is rejected.
   - Stated plainly (no false claim): this trigger does NOT and cannot identify whether the `UPDATE` came from `fn_apply_reversal` or from a direct SQL statement â€” PostgreSQL triggers have no reliable caller identity beyond `session_user`/`current_user`, both of which read as the function OWNER inside a `SECURITY DEFINER` function and as the session role otherwise, which is spoofable context, not a security boundary. The caller restriction ("only the function flips postedâ†’reversed") is therefore enforced by item 1 (grants): neither the app role nor the invoker role can issue the `UPDATE` at all, so the only reachable path to the trigger's reversal branch through the application is the definer function running as owner. The trigger is defense-in-depth: it additionally constrains the function's own writes, so a function bug producing any other transition still aborts.
   - `trg_voucher_line_locked`: `BEFORE INSERT OR UPDATE OR DELETE ON voucher_lines FOR EACH ROW` â€” allowed ONLY while the parent is in (`draft`, `edit_requested`); line writes in `edit_requested` occur solely inside `fn_apply_authorized_edit`'s transaction, which returns the parent to `pending_approval` in the same transaction. Writes with a parent in `pending_approval`, `approved_for_posting`, `posted`, `reversed`, `rejected`, or `cancelled` are rejected with no exception path â€” this holds for every role reaching the trigger, including calls issued inside definer functions, so no function can smuggle a line-write into a saved/approved/posted voucher outside the single authorized-edit path. Reversals and adjustments NEVER write to the original voucher's lines; they post a NEW voucher.
3. **Reversal entry point:** the only reachable writer of the `posted â†’ reversed` flag through the application is `fn_apply_reversal` as specified in Â§3 (owner, grants, `search_path`, validation). It cannot alter amounts, accounts, or lines.
4. **Audit rows:** the app role has no `INSERT`/`UPDATE`/`DELETE` grant on `audit_log`, and the invoker role has no `INSERT`/`UPDATE`/`DELETE` grant on it either â€” audit rows are written exclusively inside the migration-owned transition functions (same transaction as the state change, attributed to the server-resolved actor), with a `BEFORE UPDATE OR DELETE â€¦ RAISE EXCEPTION` trigger; application-issued inserts never occur.
5. **Documented limitation â€” direct owner/superuser access:** a session authenticated as the database owner or a superuser CAN bypass all of the above (`DISABLE TRIGGER`, `GRANT`, direct `UPDATE`, arbitrary function calls) â€” no trigger, grant, or function can prevent the highest-privilege database actor from acting on its own database. This is controlled, not prevented: (a) no application, test, service, or invoker credential ever holds owner/superuser privilege; (b) owner credentials live sealed (server secret store, CLI/maintenance access only per PERMISSIONS.md Â§Â§5/7 and plan.md Â§10B-B10 custodians); (c) owner-level logins and DDL are logged (PostgreSQL connection + statement logging reviewed in Phase 9); (d) tampering is DETECTED via the hash-chain verifier, nightly subledgerâ†”GL reconciliation, and off-server backups â€” a silent rewrite breaks the chain and the reconciliation gate. Tests cannot simulate a hostile superuser from a least-privilege role; instead suite 1C/7 asserts the enforceable proxies: grants (`has_table_privilege` false for app/invoker UPDATE/DELETE), triggers present and enabled, function owner/attributes/`search_path`/EXECUTE grantees exact, and no appâ†’invoker membership.

## 6. Numbering and allocation constraints (inconsistency resolved)

**Resolution:** business numbers are unique **within** `(type, financial-year)` scope, not globally. Global uniqueness is provided by surrogate `id` (PK). Rationale: FY-scoped restarts are required by college numbering practice and by "financial-year-based numbering where required"; global uniqueness would forbid restarts and contradict the requirement.

- `number_sequences(id, doc_type, fy_idâ†’financial_periods, last_number)` â€” one row per scope; incremented with `SELECT â€¦ FOR UPDATE` inside the posting txn; gaps on rollback are acceptable and documented (never reuse numbers).

- **Cross-module source-event dedupe (one economic event â†’ at most one posting):** matching amounts alone NEVER identify duplicates.   - `collection_points(id, code UNIQUE, name, cash_account_idâ†’cash_bank_accounts, is_active)` â€” each cash collection counter/point (e.g. fee counter) is a registered scope; bank instruments are scoped by issuing/drawee bank.

Identity rules DIFFER by kind (one rule per instrument semantics â€” never a single global key, never bare amount matching):
